# Excel初期取込 (#9)

`/imports/excel` で XLSX を解析し、シートごとの口座を選んでから取込を実行する。解析とマッピングでは取引を作らない。アップロードファイル自体は保存しない。監査用にファイル名、SHA-256、シート名、行番号、安全な既知列、fingerprint を保持する。

| シート | 現在の処理 |
| --- | --- |
| ANA、JAL、えりANA | 日付・内容・数量/入出・残高を持つ履歴列を取引候補にする。繰越は opening balance、負数は out とする。名義を含む口座は画面で明示選択する。 |
| ポイント積立、ポイント利用 | 履歴列だけを候補化する。制度と口座を画面で明示選択し、native 数量であることを確認するまで `needs_review` にする。集計欄を読まない。 |
| ANA移行、JAL移行 | 行別プレビューと口座・数量・状態の明示確認後、移行グループ/ステップを保存する。処理中/完了済みは既存台帳取引へ紐づけ、残高を再計上しない。 |
| ポイントマイル状況 | native数量と制度を確認し、新規の交換ルールversionを保存する。実質レートのみ/期間不明campaignは保留する。 |
| プレ商品券 | 列定義の専用マッピングが未実装のため `needs_review`。#21で対応する。 |
| チャージルール、リボ活、visa割、年間利用、支払計画、ルーチン | 対象外。 |

対象のローカル XLSX でシート名・ヘッダー・列型だけを確認し、JAL の H/I 列、ANA の I 列、ポイント履歴の A〜C 列を専用マッピングに反映した。個人情報や実残高はテスト・リポジトリへ保存していない。数式セルは計算もキャッシュ値の採用もせず無視する。日付や数量が欠ける繰越行は保留し、プレビューで値を明示補正してから取込できる。

ヘッダーを認識できないシートは行位置を推測せず `needs_review` にする。メール、電話、ログイン情報等の列を保管しない。認識列の値に含まれるメールと電話も伏せる。同一内容の正当な複数行はシート内の出現順を fingerprint に含める。未実行プレビューは再アップロードを妨げない。

## 口座別の重複判定 (#18)

解析直後は取込先が未確定なので、ファイルchecksumの警告だけを表示し、行を重複扱いにしない。`import_records.row_fingerprint` は従来と同じシート名・種別・sanitize済み値・出現順による元行の識別子を維持する。

口座を選択した後、`account-v1:` + SHA-256（口座ID + `:` + 元行fingerprint）を `imported_fingerprints` の業務キーとして照合する。口座IDは制度・名義を含む口座を識別するため、別口座の同じ履歴はそれぞれ取込可能で、同じ口座への改名ファイルの再取込はスキップする。口座作成予定も、同じ制度・名義・ラベルの既存口座があればそのIDで判定し、新規作成はcommitまで行わない。

commit時も行と口座をロックし、同じ業務キーの一意制約と取引登録を同じtransactionで処理する。失敗時はキーと取引がともにrollbackする。同じbatchの二重実行も取引を重ねず、取込済み行の状態を保持する。

プレビューの重複行は口座を選び直して再判定できる。業務取込済み行の口座は変更できない。既存取込済み行を含む再取込の残高検算では、重複行もExcel履歴の計算に含め、残高へ再反映しない。

### 既存キーの移行とデプロイ

`2026_10_02_000001_scope_imported_fingerprints_to_accounts` は、既存キーを削除せず、実際に作成された `benefit_transactions` の口座IDと元行fingerprintから口座別キーへ変換する。プレビューのマッピング値ではなく、targetとimport_record_idが一致する取引を正本とする。口座を解決できない履歴があれば全更新をrollbackし、該当import record IDを示してmigrationを停止する。キーを消して再実行しない。

デプロイ先でバックアップを取得し、旧コードのWeb・CLI取込を停止してから新コードを配置する。`php artisan down`、新コードの配置、`php artisan migrate --force`、cache更新、`php artisan up`の順とし、取込CLIも再開前に新コードへ切り替える。ローカルから本番DBへ接続しない。

rollbackは口座別キーを元行キーへ戻す。同じ元行を別口座へ取り込んだ後は旧方式の一意キーで表せないため、履歴を変更する前にrollbackを拒否する。この場合はmigrationを維持した互換コードで復旧する。新方式のキーを削除したり、旧コードだけを戻したりしない。

行に制度名がある場合は、正式名、シート名を scope とする別名、共通別名の順で解決し、選択口座の制度と一致しなければ `needs_review` にする。未知の別名は制度設定で登録後、同じ batch を再マッピングできる。

既存口座がない場合は制度・名義・ラベルをプレビューで指定する。取込実行時に初めて口座を作成し、同じ batch の後続行で再利用する。

残高不一致は明示確認が必要。取込後の訂正は既存の取消取引などで行い、batch 全体を物理削除しない。元数量の意味や状態遷移を確定できない移行・ルール行は明示補正まで要確認に残す。商品券シートの業務取込は#21で対応する。

## 移行・交換ルールの明示取込 (#20)

`TransferSheetImporter` はANA移行/JAL移行、`ConversionRuleSheetImporter` はポイントマイル状況を担当する。先頭30行で元・先の制度ヘッダーを確認し、認識できた安全な列だけを行単位で保存する。未知の列やPII列、数式セル、参考URLは取り込まない。未知のヘッダー構成はシート単位の要確認に残す。プレビュー段階では業務データを作らない。

| シート | 主な認識列 | 画面で必ず確認する内容 |
| --- | --- | --- |
| ANA移行/JAL移行 | 移行元/移行先、ポイント数・元数量、ポイント相当、マイル相当、手続開始日、移行完了予定日、移行完了日、ステータス、native先予定数量・着弾数量 | 元・先口座（制度・名義）、native単位確認、状態確認。必要に応じ行別に数量・日付・状態を補正し、換算先制度と既存台帳取引を指定する |
| ポイントマイル状況 | 交換元/優先交換先、交換元数量/交換先数量、交換下限、実質レート、条件・手順・所要時間、キャンペーン限定・開始/終了日 | 元・先制度、native交換数量、既存のルール系列または新規系列。有効化は明示チェックする |

### 数量と状態

「ポイント相当」は参考原文として保持し、native source quantityには変換しない。「マイル相当」はplanning equivalentだけに使い、予定/実着弾数量に流用しない。換算数量がある場合は換算先制度も選択する。数量はDecimal、小数4桁以内とし、元数量は正数、先数量は0以上を要求する。

予定/手続中/完了/済の表記を候補化するが、状態確認なしでは取込できない。空欄をcompletedにしない。予定は申請・完了日を持たず、処理中は申請日、完了済みは申請日・完了日・実着弾数量が必要。日付の逆転も要確認にする。既存口座/制度を明示選択し、元行の正式名・scope付きalias・共通aliasとの一致を検証する。未知の制度名はalias設定後に再マッピングできる。Importerが勝手に口座や制度を作ることはない。

1行から独立した移行グループと1ステップを作る。複数行を同じ多段移行へ自動統合しない。行別の確認内容は再マッピング後も保持し、skipも行単位で継続する。取込済み行は修正できない。

### 台帳の二重計上防止

予定移行は残高を変更しない。処理中・完了済みの移行は、先に取り込まれた履歴の取引IDを行別に指定して登録する。このモードで新しい出金/入金取引は生成しない。

- 処理中: 元口座・native数量・申請日が一致する既存出金（use/transfer_out）を1件指定する。
- 完了済み: 上記出金に加え、先口座・native実数量・完了日が一致する既存入金（earn/transfer_in）を1件指定する。実数量0の場合は入金を指定しない。
- 他の移行/出品へ紐づけ済み、取消済み、方向・口座・数量・日付が異なる取引は使えない。分割された複数取引を1ステップへ自動集約することもない。

取引を解決できなければneeds_reviewに残す。実行時に口座と取引をロックして再確認し、既存取引の数量・日付・残高・source/import_record情報を維持してtransfer_step_idを設定し、取引種別をtransfer_out/inにする。処理中の着弾/返却は既存の移行サービスで操作できる。直接取消の可否もロック取得後に再確認するため、紐づけ前に読み込んだ古いモデルから迂回できない。

### 交換ルールの版管理

実質レートだけではnative交換数量を確定しない。交換数量が欠ける行は補正までneeds_reviewに残す。所要時間の原文を保持し、`3日`、`2〜5日`のように範囲が明確な表記だけ日数を補完する。

キャンペーン限定列、または条件中の「キャンペーン時のみ/キャンペーン限定」は期間確認を要求する。期間不明・逆転はneeds_reviewで停止する。新しい版は初期状態で無効、有効化は明示チェックする。既存系列を選ぶ場合は元・先制度との一致を確認し、系列をロックしてversion_noを採番する。既存版の数量・条件・activeは変更しない。

### 重複・失敗・互換性

元行fingerprintは既存方式と同じくシート名・種別・sanitize済み認識列・出現順から生成し、ファイル名を含めない。取引の`account-v1:`キーは変更しない。

- 移行: `transfer-v1:` + SHA-256（元口座ID・先口座ID・元行fingerprint）
- ルール: `rule-v1:` + SHA-256（元制度ID・先制度ID・元行fingerprint）

プレビューで明示マッピング後に照合し、commit時は既存の一意キーと業務登録を同じ行transactionで処理する。同じ行を別口座ペアへ取り込むことは可能。同じ口座ペア・制度ペアの改名再取込は重複になる。別batch/同一batchの同時取込も二重生成しない。同じ台帳取引を異なる元行へ紐づけようとする競合は、片方だけを保存し、もう片方はerrorにする。正常行を保持し、失敗行だけ修正して再実行できる。

新規migrationは不要。既存の口座fingerprint移行を適用したmainから配置する。新しいtransfer/ruleキーが保存された後、#18以前の旧fingerprintへのrollbackは行わない（旧migrationは口座取引として解決できない履歴を拒否する）。業務履歴やfingerprintを削除して旧コードへ戻す方法は使わず、新キーを維持できるコードで復旧する。
